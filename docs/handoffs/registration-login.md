# Registration requires explicit login

- Root cause: registration called `IssueAsync`, the controller set a refresh cookie, and frontend used `loginSession(input, true)` to accept tokens/profile and route to member/product.
- Backend registration now returns internal `RegistrationResult(ProfileDto User)` without issuing tokens or LastLoginAt. Account/customer role/cart/membership/referral/affiliate creation remains transactional. Public web/native register response is HTTP201 with `{data:{message}}`; no user profile, credentials or Set-Cookie. Login/refresh response contracts remain unchanged.
- Frontend uses separate `registerAccount` / auth-store `register`, which never accepts a session or publishes a profile. Registration resets the form and replaces the route with `/login?registered=1`, preserving referral/product/service/affiliate context. Login displays an accessible success banner, then requires credentials before setting user state or routing to member/product.
- CLI first-admin provisioning handles the new registration result; existing-account provisioning still verifies credentials with login and revokes that temporary session afterward. The refresh regression now explicitly logs in before testing rotation/replay.
- Backend registration regression proved the original defect before fixing it. Full backend suite: 140 passed; verifies no refresh-token rows before login, no LastLoginAt, web/native confirmation-only response and no cookies. Full frontend suite: 146 passed; includes a legacy credential-bearing register response that must not populate a session/profile. TypeScript, lint and web export passed.
- Browser end-to-end against disposable PostgreSQL/local API: register → login success banner; account count1/session count0/login count0. Wrong password stays on login. Correct password → member page/profile, with the first session created only then. No production accounts or sessions were created/modified by these tests.
- No migration needed. Deploy backend and frontend together: old registration endpoint issues an HttpOnly cookie even if a new frontend ignores its credential-bearing body. Existing legitimate sessions are not retroactively revoked. Changes have not been pushed or deployed by this task.
