# Admin-managed platform fee

- Singleton `PlatformFeeConfigurations` stores `PlatformFeeRate` as numeric(7,4), UUID revision, optional updated-at/updating account. Migration `20261112024901_AdminManagedPlatformFee` seeds 0% (matching current workspace configuration), with singleton/range constraints and account FK. Existing seller settlements are untouched. Down removes settings only.
- `GET /api/admin/settings/platform-fee` returns the standard ApiResponse envelope with `data.platformFeeRate`, `revision`, `updatedAt` and `updatedByAccountId`. Both GET and PUT require a JWT Admin/SuperAdmin role plus an active account/current database admin role.
- `PUT` body: `{ "platformFeeRate": 0.05, "expectedRevision": "<revision from GET>" }`. Rate is a fraction: 0.05 = 5%, 0 = 0%, 1 = 100%; at most four effective decimal places. Missing fields/invalid rates -> 400; stale revision -> 409 (reload); unauthorized role/inactive account -> 403. PUT returns updated configuration. No-op keeps revision/audit unchanged; real updates rotate revision and add UPDATE_PLATFORM_FEE audit entries.
- Future admin UI: GET current value, display `rate * 100` percent, send the input divided by 100 rounded to four decimal places with the fetched revision, then use the returned revision for subsequent edits. No admin UI is built in this change.
- FinanceService reads the DB rate in its existing completed/paid order transaction, once per accrual; money rounding stays two decimals, AwayFromZero. Fees use seller-order goods total, excluding shipping. Rate changes affect future accruals, including older orders not yet completed; existing accrued settlement amounts stay fixed and repeat accrual remains idempotent. There is no environment fallback/cache; missing settings fail the transaction.
- Removed runtime requirement/example for Settlement__PlatformFeeRate; the old value in an existing .env is ignored. Settlement__HoldDays remains separate. No secret .env edits. DI registers IPlatformFeeConfigurationService.
